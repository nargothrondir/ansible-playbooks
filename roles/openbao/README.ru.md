# openbao

## Description

Разворачивает [OpenBao](https://openbao.org/) на хосте панели через Docker
Compose, со встроенным Raft-хранилищем. OpenBao — хранилище runtime-секретов,
которым пользуется флот (issue #2). Оно единственное: зашифрованных файлов в
репозиториях больше нет.

**Роль только разворачивает.** `bao operator init` печатает Shamir-доли и
root-токен ровно один раз — они не должны проходить ни через Ansible, ни через
лог Semaphore, ни через этот репозиторий, поэтому его запускает оператор.
Повторный прогон роли против уже инициализированного хранилища безопасен:
здесь нет ничего, что трогает init или unseal.

### Две вещи, которые надо знать до использования

**Любой перезапуск запечатывает хранилище.** Распечатывание ручное (Shamir,
3 из 5 — решение из #2). Изменение конфига дёргает handler, контейнер
поднимается запечатанным, и все плейбуки, читающие секреты, падают, пока
кто-нибудь не введёт доли. Правка конфига здесь — операционное событие, а не
рутинный прогон. Перезагрузка хоста даёт тот же эффект.

**`disable_mlock` включён принудительно, и это компромисс.** В официальном
образе нет `setcap`, а процесс работает под непривилегированным `openbao`,
поэтому заблокировать память он не может даже с `--cap-add=IPC_LOCK`; с
включённым mlock он просто не стартует. Следствие: память с расшифрованными
секретами может попасть в swap. Компенсируется на хосте — zram держит
вытесненные страницы в RAM (см. роль `common`), дисковый swap не держит.

### Как до него добираются клиенты

Клиенты-контейнеры (сегодня — Semaphore, читающий секреты от имени плейбуков)
входят в сеть `openbao_network` и обращаются к API по имени сервиса:
`http://openbao:8200`. Сеть создаёт сама роль, поэтому у имени нет
compose-префикса проекта и роль `semaphore` может подключиться к ней через
`semaphore_external_network`.

Опубликованный порт на петле для контейнеров **не подходит**. Порт, привязанный
к `127.0.0.1`, из контейнера недостижим; публикация на шлюзе моста открыла бы
хранилище секретов всем контейнерам хоста. Выделенная сеть доступна только тем,
кто в неё явно включён.

Данные Raft лежат в именованном Docker-томе `openbao_file`, смонтированном в
`/openbao/file` — **не** в `openbao_data_dir`, где лежат только compose-файл и
отрендеренный конфиг.

Точка монтирования выбрана не произвольно. Docker наполняет свежий именованный
том из каталога образа вместе с владельцем, поэтому путь, который образ уже
объявляет (`/openbao/file`), работает. Путь, которого в образе нет, даёт
каталог, принадлежащий root, и сервер — работающий под непривилегированным
`openbao` — падает с `failed to open bolt file: permission denied`.

### Учётка оператора: подпись сертификата с ноутбука

Плейбуки подписывают SSH-сертификаты через AppRole Semaphore. Человеку за
ноутбуком нужен ровно этот вызов и ничего больше из того, что достаёт та
AppRole, поэтому `playbooks/openbao-setup.yml` держит для него отдельную
личность:

- политика `ssh-sign-operator` — единственный путь, `ssh/sign/fleet`. Прочитать
  ею нельзя ни один секрет, выпустить хостовый сертификат — тоже.
- метод входа `userpass` и учётка с именем из `openbao_operator_username`.

Userpass, а не вторая AppRole, по одной причине. Key ID сертификата строится из
`token_display_name`, а любой вход по AppRole сообщает там буквальную строку
`approle` — и в логе ноды остаётся, что вошло *что-то*, но не кто. С userpass та
же строка называет учётку.

**Учётку плейбук не создаёт.** Для создания нужен пароль, а твой пароль не
должен проходить через плейбук, лог или этот репозиторий. Поэтому владение
разделено: пароль твой, права — плейбука.

Создаётся один раз, на панели. Ввод молчит — при наборе ничего не отображается:

```bash
read -rs -p 'new password: ' P && echo && printf '%s' "$P" | docker exec -i openbao bao write auth/userpass/users/operator password=- && unset P
```

Успех печатает `Success! Data written to: auth/userpass/users/operator`.

Держи фразу короче 72 байт. Более длинный ввод bcrypt отвергает, а
`updateUserPassword` возвращает это как внутреннюю ошибку, а не как ошибку
валидации, — API ответит 500, ничем не назвав причину (читано на v2.6.2).

Учётка создаётся **без** политик, то есть не может вообще ничего, пока плейбук
не выдаст ей единственную. Промежутка, в котором прав больше нужного, не
возникает:

```bash
ansible-playbook playbooks/openbao-setup.yml -e ansible_connection=local
```

В конце он печатает `Operator account operator exists, policy ssh-sign-operator`.

Повторные прогоны безопасны и дальше: обработчик применяет пароль только
`if password != "" || passwordHash != ""`, поэтому обновление без пароля
оставляет сохранённый хеш нетронутым.

**Сетевого доступа это не даёт.** API опубликован на петле панели, значит
учётка работает с панели и больше ниоткуда. Дотянуться до неё с ноутбука —
отдельное решение о публикации порта в меш, а оно же является решением про
всех остальных пиров этого меша.

### Аварийный доступ: как вернуть root-токен

OpenBao **объявил неаутентифицированные эндпоинты восстановления root
устаревшими в 2.5.3 и выключает их по умолчанию.** Поэтому
`bao operator generate-root -init` отвечает `403 permission denied`, и после
отзыва последнего root-токена вернуть его без процедуры ниже нельзя. Проверено
на 2.6.1 на собственном опыте.

Наличия Shamir-долей **недостаточно**.

**`bao operator generate-root` для этого не годится.** Все три его подкоманды
обращаются к `/sys/generate-root-token/*`, а переключатель открывает
`/sys/generate-root/*` — другой путь, остающийся под 403. Работайте с API
напрямую. Проверено целиком на 2.6.1, 2026-08-04.

```bash
# 1. открыть дверь; контейнер перезапустится и поднимется ЗАПЕЧАТАННЫМ
ansible-playbook playbooks/openbao.yml -e openbao_allow_root_generation=true
docker exec -it openbao bao operator unseal            # x3

# 2. начать попытку — запомнить nonce и otp из вывода
docker exec -it openbao bao write -f sys/generate-root/attempt

# 3. передать три доли. key=- читает значение из stdin, поэтому доля не
#    попадает ни в аргументы, ни в историю; read -rs скрывает её и с экрана.
read -rs SHARE && printf '%s' "$SHARE" | docker exec -i openbao bao write sys/generate-root/update nonce=<nonce> key=- && unset SHARE
#    повторить x3; третья вернёт encoded_root_token

# 4. расшифровать самостоятельно. `-decode` тоже дёргает сломанный путь, а тут
#    всего лишь base64 и XOR с OTP.
python3 -c "
import base64
enc='<encoded_root_token>'; otp='<otp>'
raw=base64.b64decode(enc+'='*(-len(enc)%4))
print(''.join(chr(b^ord(o)) for b,o in zip(raw,otp)))
"

# 5. закрыть обратно — второй перезапуск и второе распечатывание
ansible-playbook playbooks/openbao.yml
docker exec -it openbao bao operator unseal            # x3
```

`encoded_root_token` и `encoded_token` — одно значение под двумя именами,
первое legacy-алиас.

**Считайте encoded-токен и OTP одним секретом.** По отдельности бесполезны, но
вместе они **и есть** root-токен: шаг 4 — арифметика, доступная кому угодно.
Не храните и не передавайте их одним каналом.

Два перезапуска и два распечатывания. Хранилище на это время недоступно.

По умолчанию переключатель выключен, как и у апстрима: пока он включён, любой,
кто дотянется до API, может *начать* попытку без токена. Завершить её без
кворума долей нельзя, так что это помеха, а не компрометация — но держать
постоянную дверь ради операции раз в год невыгодно.

### Запись секрета в хранилище

Значению не нужно появляться на экране или проходить через буфер обмена — это
заодно снимает риск потерять символ на переносе строки: длинный JWT руками
не выделяется.

**Одно поле.** `read -rs` не отображает ввод и не оставляет его в истории
шелла; конвейер отдаёт значение в CLI через stdin, так что оно не попадает и в
список аргументов:

```bash
read -rs -p 'setup key: ' V && echo && printf '%s' "$V" | docker exec -i openbao bao kv put infra/netbird setup_key=- && unset V
```

**Несколько полей — обязательно, если в секрете их больше одного.**

`bao kv put` **заменяет секрет целиком**. Запись по одному полю молча стирает
всё записанное раньше, поэтому многополевой секрет пишется одним вызовом, JSON
через stdin:

```bash
python3 -c "import json,sys,getpass; json.dump({'bot_token': getpass.getpass('bot_token: '), 'chat_id': input('chat_id: ')}, sys.stdout)" | docker exec -i openbao bao kv put infra/telegram -
```

`getpass` для секретных частей, `input` для несекретных — chat id не
чувствителен и набирать его вслепую незачем. Одиночный `-` вместо пар
ключ-значение заставляет CLI прочитать весь секрет как JSON со stdin. Проверено
на 2.6.1 (2026-08-05, таблица hawser на пять хостов одним вызовом).

**Добавление поля к секрету, где уже есть другие:** нужен `kv patch`, а не
`kv put`. Patch дописывает, поэтому поля можно класть по одному — с `put` это
молча стёрло бы всё записанное раньше:

```bash
read -rs -p 'value: ' V && echo && printf '%s' "$V" | docker exec -i openbao bao kv patch infra/semaphore access_key_encryption=- && unset V
```

`kv patch` требует больше, чем чтение и запись по пути данных: он делает
предварительную проверку прав, поэтому его политике нужны ещё

```hcl
path "sys/internal/ui/mounts/*" { capabilities = ["read"] }
path "sys/capabilities-self"    { capabilities = ["update"] }
```

Без них CLI падает с 403 на `sys/internal/ui/mounts/...`, где про патч не
сказано ни слова. Измерено 2026-08-20.

**Проверка без вывода значения.** Сравни сохранённую длину с ожидаемой — 44 для
base64-ключа в 32 байта, и так далее:

```bash
docker exec -i openbao bao kv get -field=access_key_encryption infra/semaphore | wc -c
```

`docker exec -i`, никогда `-it`: с выделенным псевдотерминалом pty вставляет
возвраты каретки на переносах, и счёт байтов получается завышенным.

И убедись, что прежние поля уцелели — если поле, которое было, пропало, значит
`patch` сработал как `put`, и его надо вернуть прежде всего остального:

```bash
docker exec openbao bao kv get -format=json infra/semaphore | python3 -c 'import sys,json;print(", ".join(json.load(sys.stdin)["data"]["data"].keys()))'
```

### Удаление поля из многополевого секрета

Нужно, когда в таблице накапливаются записи для хостов, которых больше нет.
`bao kv put` заменяет секрет целиком, поэтому поле удаляется записью всего
остального без него — чтение-правка-запись одним конвейером, причём уцелевшие
значения проходят через `python3`, а не через экран:

```bash
docker exec -i openbao bao kv get -format=json infra/hawser | python3 -c "
import sys, json
d = json.load(sys.stdin)['data']['data']
for k in ('lab-1', 'test'):
    d.pop(k, None)
json.dump(d, sys.stdout)
" | docker exec -i openbao bao kv put infra/hawser -
```

Кортеж в строке `for` перечисляет удаляемые поля; `pop(k, None)` превращает
отсутствующее имя в пустую операцию вместо ошибки. Проверка —
`bao kv get infra/hawser`: названных полей нет, все остальные сохранили свои
значения.

`bao kv patch` короче, но его метод по умолчанию требует права `patch`, которого
политика `hawser-write` не даёт (см. её текст в `playbooks/openbao-setup.yml`).
Явная чтение-правка-запись выше работает с политикой как она есть.

**Удаление поля — не стирание.** KV v2 хранит предыдущие версии, поэтому старое
значение остаётся доступным через `bao kv get -version=<n> infra/hawser`.
Чистка — это гигиена; утёкший ключ закрывается ротацией, то есть заменой токена
везде, где он используется, а не удалением записи здесь.

## Бэкапы и учение по восстановлению

`playbooks/openbao-backup.yml` снимает снапшот через
`sys/storage/raft/snapshot` и отправляет его в Telegram, ежедневно, по
расписанию Semaphore. Это всё хранилище одним файлом: KV, политики,
конфигурация auth и приватный ключ SSH CA — который не отдаёт ни один API и у
которого больше нет никакой копии.

**Каталог данных бэкапить нельзя.** Встроенный Raft — это BoltDB, открытая и
записываемая работающей службой; пофайловая копия снимается посреди транзакции
и восстанавливается разорванной базой. Согласованный образ даёт только
endpoint снапшота, и снимается он онлайн.

### Что внутри

Снапшот — это gzip-сжатый tar из трёх файлов, согласно
`internal/physical/raft/snapshot/archive.go` в апстриме:

| | |
|---|---|
| `meta.json` | метаданные снапшота от Raft, в JSON |
| `state.bin` | само хранилище, запечатанное барьерным ключом |
| `SHA256SUMS` | суммы SHA-256 двух предыдущих |

Расширение `.snap`, а не `.tar.gz`, выбрано намеренно. Формально это
действительно gzip-tar, но распаковывать его никогда не нужно: `state.bin`
зашифрован, править там нечего. Единственное осмысленное действие — отдать
файл в `bao operator raft snapshot restore`, и расширение должно вести туда.

Плейбук бэкапа проверяет файл дважды, и проверки отвечают на разные вопросы.
`SHA256SUMS` изнутри архива говорит, что файл на диске цел. Затем отправленный
документ **скачивается обратно и сверяется по SHA-256** с отправленным — это
говорит, что в чате лежат те же байты, что ушли.

Вторая проверка появилась потому, что её отсутствие скрыло настоящий отказ.
`uri` с `form-multipart` в ansible-core 2.20.8 кодирует файловую часть в base64
и отключить это нечем, поэтому все отправленные так снапшоты были base64-**текстом**
снапшота: целые на диске, загруженные без ошибок, зелёные в отчёте и
невосстановимые. Отправка переведена на `curl`.

Ни одна из проверок не говорит, восстановится ли снапшот. Это говорит только
учение.

### Сколько стоит снапшот без ключей распечатывания

Нисколько. Он запечатан барьерным ключом — потому и допустимо отправлять его в
чат. Следствие важнее самого факта: **бэкап — это ключи распечатывания.**
Потеряешь их, и все снятые когда-либо снапшоты станут шумом. Их место в
менеджере паролей, вне этого флота, и больше нигде.

Верно и обратное, менее очевидное: каждый отправленный снапшот остаётся в чате
навсегда, поэтому утечка ключей делает читаемой всю историю разом, включая
ротированные с тех пор секреты. Это известная цена назначения без ротации.

### Учение

**Прилетевший в чат файл доказывает отправку, а не восстановление.** Большего
автоматика доказать не может: восстановление требует ключей распечатывания, а
у Semaphore их нет и быть не должно. Делается руками, на временном контейнере,
никогда против живого хранилища. Раз в квартал — разумно; после любого
изменения печати — обязательно.

Скачай свежий снапшот из чата на панель и подними временный экземпляр
**с raft-хранилищем**. `-dev` не годится: он работает на inmem, а обработчик
восстановления отказывает всему остальному —

```go
raftStorage, ok := b.Core.underlyingPhysical.(*raft.RaftBackend)
if !ok {
    return logical.ErrorResponse("raft storage is not in use"), ...
}
```

Образ кладёт `BAO_LOCAL_CONFIG` в `/openbao/config/local.json` и грузит каталог,
поэтому вся конфигурация помещается в одну переменную окружения. Версия образа —
та, что названа в подписи снапшота: снятое новой версией может не встать в
старую.

```bash
docker run -d --name bao-drill -p 127.0.0.1:8300:8200 -e BAO_ADDR=http://127.0.0.1:8200 -e BAO_LOCAL_CONFIG='{"storage":{"raft":{"path":"/openbao/file","node_id":"drill"}},"listener":[{"tcp":{"address":"0.0.0.0:8200","tls_disable":true}}],"api_addr":"http://127.0.0.1:8200","cluster_addr":"http://127.0.0.1:8201","disable_mlock":true}' ghcr.io/openbao/openbao:2.6.1 server
```

Порт 8300 — чтобы случайно не нацелиться на живое хранилище.

Поднимается он неинициализированным, поэтому дай ему одноразовые ключи. Они
нужны лишь чтобы дойти до восстановления, которое их же и обесценит:

```bash
docker exec bao-drill bao operator init -key-shares=1 -key-threshold=1
```

Распечатай тем ключом, что он напечатал, и восстанавливай:

```bash
docker exec bao-drill bao operator unseal <одноразовый ключ>
```

```bash
docker cp <снапшот> bao-drill:/tmp/drill.snap
```

```bash
docker exec -e BAO_TOKEN=<одноразовый root-токен> bao-drill bao operator raft snapshot restore -force /tmp/drill.snap
```

`-force` обязателен всегда, когда печать цели не совпадает с печатью снапшота —
здесь это всегда так. Описание из исходника: *bypasses checks ensuring the
current Autounseal or Shamir keys are consistent with the snapshot data*.

**Теперь одноразовые ключи недействительны.** Контейнер стал прежним хранилищем
и запечатался. Распечатывай **исходными** долями из менеджера паролей — ради
этого шага учение и проводится:

```bash
docker exec -it bao-drill bao operator unseal
```

Повторить до исходного кворума, затем:

```bash
docker exec bao-drill bao status
```

**Распечаталось — это и есть результат.** Значит мастер-ключ внутри снапшота
открывается теми самыми долями: снапшот — настоящее хранилище, а не похожий на
него файл. Вместе с проверкой SHA256SUMS на этапе бэкапа это предел доказуемого
без токена.

Чтобы пойти дальше и прочитать данные, войди через AppRole, как это делает любой
плейбук. `role_id` лежит в инвентаре и секретом не является; `secret_id` нужен
такой, который существовал на момент снятия снапшота — потянуться за свежим и
есть типичная ошибка, в восстановленном хранилище его не будет:

```bash
docker exec bao-drill bao write auth/approle/login role_id=<role_id> secret_id=<secret_id>
```

```bash
docker exec -e BAO_TOKEN=<вернувшийся токен> bao-drill bao kv get -field=public_key infra/ssh_ca
```

Учение зачтено, если напечатался тот публичный ключ CA, которому доверяет флот.
Потом убери контейнер вместе с анонимным томом:

```bash
docker rm -fv bao-drill
```

Восстановление на настоящей панели — та же форма без временного контейнера:
развернуть `openbao.yml`, инициализировать, восстановить с `-force` и распечатать
исходными долями. Ключи, напечатанные при инициализации, восстановление
обесценивает.

## Dependencies

Зависимостей в `meta` нет, но Docker должен быть уже установлен — сначала
примените роль `docker`. Используется коллекция `community.docker`
(`docker_compose_v2`, `docker_container_exec`), запиненная в
`requirements.yml`.

## Example

```yaml
- name: Deploy OpenBao
  hosts: panel
  become: true
  roles:
    - openbao
```

**Не `hosts: control`.** Хост `controller` объявлен как
`ansible_connection: local`, то есть «там, где выполняется Ansible» — а это
*контейнер* Semaphore, когда запуск идёт шаблоном, а не панель. Роль должна
целиться в сам хост панели.

Затем, оператором, один раз:

```bash
docker exec -it openbao bao operator init
```

Доли храните офлайн **и отдельно от любой резервной копии хранилища**:
Raft-снапшот зашифрован мастер-ключом, поэтому бэкап — это снапшот *и* доли
вместе, а по отдельности каждая половина бесполезна (#7).

После каждого перезапуска:

```bash
docker exec -it openbao bao operator unseal   # повторять до порога
```

## Supported OS

Debian 12/13, Ubuntu current LTS. Проверяется assert'ом на `os_family`.
