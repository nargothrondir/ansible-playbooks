# Роль: xanmod

[🇬🇧 English](README.md) · 🇷🇺 Русский

## Описание

Устанавливает производительное ядро [XanMod](https://xanmod.org/) из
официального APT-репозитория XanMod (ключ подписи →
`/etc/apt/keyrings/xanmod.asc`, deb822-источник →
`/etc/apt/sources.list.d/xanmod.sources`). Идемпотентна.

**Требуется перезагрузка**, чтобы загрузиться в новое ядро; роль сама НЕ
перезагружает. Активирует его роль `upgrade`, когда обнаружит,
что работающее ядро перестало быть новейшим установленным (или ручная
перезагрузка).

Замечание: `deb.xanmod.org` — сторонний зеркальный домен и в некоторых регионах
периодически блокируется (см. issue #3 для ноды `ru`).

## Переменные

| Переменная | По умолчанию | Описание |
|------------|--------------|----------|
| `xanmod_variant` | `x64v3` | Уровень CPU/PSABI: `x64v1`…`x64v4` либо `auto` — прочитать по флагам процессора |
| `xanmod_variant_max` | `x64v3` | Потолок, применяемый когда `xanmod_variant` равен `auto` |
| `xanmod_package` | `linux-xanmod-{{ xanmod_variant }}` | Устанавливаемый пакет |
| `xanmod_apt_arch` | `amd64` | Архитектура APT-репозитория |
| `xanmod_reboot` | `false` | Перезагрузка в новое ядро, если оно только что установлено (handler) |

### Выбор варианта

XanMod выпускает по ядру на каждый уровень микроархитектуры x86-64. Ядро,
собранное под уровень, которого у процессора нет, **не загружается**, и на VPS
это выглядит как нода, не вернувшаяся из перезагрузки, — без консоли и без
единой записи, связывающей её с вызвавшим это прогоном.

Поэтому роль определяет уровень до того, как что-либо ставит: читает
`/proc/cpuinfo` и применяет таблицы флагов из собственного скрипта XanMod
`check_x86-64_psabi.sh`. Сам скрипт не скачивается и не запускается —
воспроизвести восемь строк awk дешевле, чем выполнять полученный из сети файл от
root, и не зависит от доступности `dl.xanmod.org` с ноды, которая может стоять
за блокировками.

Из определённого уровня следует две вещи.

**Assert работает всегда.** Настроенный вариант выше возможностей процессора
останавливает игру до вызова `apt`. Нода, уже работающая на `x64v3`, имеет
уровень не ниже третьего, так что на здоровых хостах это молчит.

**`auto` включается явно.** При `xanmod_variant: auto` роль ставит
`min(определённый уровень, xanmod_variant_max)`. Не по умолчанию, потому что
смена варианта на работающей ноде — это подмена ядра, а плановый прогон такого
делать не должен; `provision-node.yml` включает его для свежих нод, как уже
включает `xanmod_reboot`.

**Потолок поставлен намеренно.** `xanmod_variant_max` по умолчанию `x64v3`, а не
максимум, о котором сообщает процессор: VPS — это не его железо. Провайдеры
переносят гостей между хостами, и ядро `x64v4` перестаёт загружаться в тот
момент, когда гость попадает на машину без AVX-512. Такая поломка приходит
оторванной от любых твоих действий. `x64v3` — это AVX2, его держит всё, что
продаётся последние десять лет, и это рекомендованная самим XanMod сборка.

Обрати внимание: роль **не** проверяет, работает ли уже ядро XanMod. `apt` с
`state: present` возвращает `ok` для установленного пакета и ничего не меняет,
так что сторожить нечего; а работающее ядро — неверный признак, потому что нода,
на которой XanMod установлен, но перезагрузки ещё не было, работает на стоковом.

## Зависимости

Нет.

## Пример

```yaml
- hosts: managed
  become: true
  roles:
    - role: xanmod
```

## Поддерживаемые ОС

Debian 12/13, Ubuntu 24.04 (`os_family == 'Debian'`), x86-64.
