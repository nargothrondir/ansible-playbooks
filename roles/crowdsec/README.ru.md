# Роль: crowdsec

[🇬🇧 English](README.md) · 🇷🇺 Русский

## Описание

Устанавливает [CrowdSec](https://crowdsec.net) и firewall-bouncer на nftables и
защищает хост от атак по **SSH** с **прогрессивными (экспоненциальными)**
банами, применяемыми локально.

Проектные решения (см. issue #31):

- **Только SSH.** Ингестится лишь коллекция `crowdsecurity/sshd`. Лог доступа
  камуфляжа на 443 намеренно **не** отслеживается — значит забанить на 443
  нечем, а бан там был бы поведенческим fingerprint'ом, которого нет у обычного
  сайта.
- **Прогрессивные баны.** Длительность бана удваивается с каждым прошлым
  решением по этому IP (`1ч → 2ч → 4ч …`), с потолком в одну неделю. Реализовано
  через `duration_expr` в `profiles.yaml` с `GetDecisionsCount`.
- **Anti-lockout whitelist.** Диапазон Netbird-mesh (и admin-IP) в whitelist,
  чтобы LAPI-трафик панель↔нода и твой доступ никогда не порождали бан.
- **Центральная LAPI заложена, но по умолчанию неактивна.** При
  `crowdsec_central_lapi_enabled: false` нода работает автономно (своя локальная
  LAPI). Включить позже — репортить в панельную LAPI по mesh, без переделки.

## Переменные

| Переменная | По умолчанию | Описание |
|------------|--------------|----------|
| `crowdsec_collections` | `[crowdsecurity/sshd]` | Устанавливаемые коллекции. По замыслу — только SSH. |
| `crowdsec_ban_base_hours` | `1` | Длительность первого бана, в часах. |
| `crowdsec_ban_cap` | `168h` | Потолок экспоненциального бана (неделя). |
| `crowdsec_ban_cap_threshold` | `7` | Число прошлых решений, выше которого действует потолок. |
| `crowdsec_whitelist_cidrs` | `[100.64.0.0/10]` | CIDR, по которым CrowdSec никогда не действует (mesh + admin). |
| `crowdsec_central_lapi_enabled` | `false` | Репортить в центральную LAPI панели (на весь флот) вместо локальной. |
| `crowdsec_central_lapi_url` | `""` | URL центральной LAPI по mesh (при активации). |
| `crowdsec_central_lapi_login` | `{{ inventory_hostname }}` | Логин машины, зарегистрированной на панели (при активации). |
| `crowdsec_central_lapi_password` | `""` | Пароль машины — класть в OpenBao при активации. |

### Почему бунсер регистрируется явно

Пакет `crowdsec-firewall-bouncer-nftables` регистрируется сам, вызывая в
postinst `cscli bouncers add` — а тому нужен живой LAPI, которым является сам
агент. Оба пакета ставятся одной транзакцией apt, поэтому на чистой машине
агент ещё не поднят в момент настройки бунсера. Регистрация тихо не удаётся, в
конфиге остаётся заглушка, и сервис падает при каждом старте:

```
level=fatal msg="process terminated with error: API error: access forbidden"
```

при пустом `cscli bouncers list`. Поймано на первом прогоне пайплайна по чистой
установке.

Роль всегда регистрировала бунсер сама — но *после* попытки его запустить.
Падение запуска обрывало плей до регистрации, так что чинить надо было порядок,
а не отсутствующий шаг.

Поэтому роль сначала поднимает агента отдельно, затем регистрирует бунсер сама
и записывает ключ, и только после этого запускает бунсер. Признаком служит
**длина** ключа, а не совпадение с текстом заглушки, — заодно это чинит
наполовину настроенную машину при следующем прогоне: устаревшая регистрация под
тем же именем удаляется и создаётся заново, потому что показать существующий
ключ `cscli` не умеет.

## Зависимости

Нет (на уровне роли). Ожидается, что `common` отработал раньше в пайплайне
(базовые пакеты, включая `python3-debian` для `deb822_repository`); для
автономных/DR-прогонов роль ставит эти пререквизиты и сама.

Активация `crowdsec_central_lapi_enabled` дополнительно требует **стороны
панели**: `cscli machines add <login>` для агента и bouncer API-ключ, выданный
на панели.

## Пример

```yaml
- hosts: nodes
  become: true
  roles:
    - role: crowdsec
      vars:
        crowdsec_whitelist_cidrs:
          - "100.64.0.0/10"     # mesh
          - "203.0.113.5/32"    # admin
```

## Поддерживаемые ОС

Debian 12/13, Ubuntu 22.04/24.04 (`os_family == 'Debian'`).
