# ssh_hardening

[English](README.md) | **Русский**

## Описание

SSH-усиление для хостов флота. Текущий объём (шаг 1 issue #30): открыть
**дополнительный порт sshd для автоматизации по ключу через NetBird-меш**.

Зачем второй порт: на пирах с включённым NB-SSH NetBird перехватывает
mesh-трафик на порт 22 (заворачивая его во встроенный JWT/SSO-сервер для
браузерного break-glass SSH из дашборда), поэтому классическая аутентификация
по ключу до sshd там не доходит. Ansible получает собственную дверь — порт,
который перехват не трогает. [Роль ufw](../ufw/README.ru.md) открывает его
только на mesh-интерфейсе; наружу он не выставляется.

Drop-in явно перечисляет и `Port 22`: первая директива `Port` отменяет
неявный дефолт, а несколько строк `Port` суммируются. Смёрженный конфиг
валидируется (`sshd -t`) до срабатывания handler'а перезагрузки.

Следующие шаги #30 (отключение паролей, root-логина, крипто-усиление) будут
расширять эту роль.

## Доверие к SSH CA флота

Необязательная вторая задача, выключенная, пока `ssh_hardening_ca_public_key`
пуста: положить публичный ключ удостоверяющего центра и велеть sshd принимать
подписанные им пользовательские сертификаты.

**Это добавляет способ входа и ни одного не убирает.** `authorized_keys` роль
не трогает, поэтому существующий ключ остаётся дверью, а сертификат, который не
прошёл проверку, просто не становится второй. Так задумано: неправильно
поставленный якорь доверия должен стоить неудавшегося опыта, а не запертой
двери. Убирается он без всякого плейбука — удалить
`/etc/ssh/sshd_config.d/20-ansible-ca.conf` и перезагрузить sshd.

Ключ пишется раньше drop-in'а, который на него ссылается: `TrustedUserCAKeys`,
указывающий на отсутствующий файл, заставляет sshd писать ошибку при каждой
попытке аутентификации. У обеих задач одно `when`, поэтому хост не остаётся с
половиной конструкции.

`AuthorizedPrincipalsFile` сознательно не настраивается. Без него sshd
принимает сертификат, среди принципалов которого есть имя целевого
пользователя, — ровно то правило, которое роль подписи в CA и так соблюдает при
выдаче.

После перезагрузки идут две проверки, и отвечают они на разные вопросы.
`sshd -t` говорит, что смёрженный конфиг разбирается; `sshd -T` говорит, что
именно он смёржил. Drop-in, который не был включён — нет строки `Include` в
`sshd_config` образа провайдера, — первую проходит, а во второй отсутствует.
Без второй проверки доверие к сертификатам выглядело бы установленным и не
делало бы ничего, а обнаружилось бы это входом, тихо откатившимся на ключ.

Зелёный прогон **не** доказывает, что вход по сертификату работает. Он
доказывает, что sshd отдаёт директиву. Вторая половина доказывается отдельно —
[playbooks/openbao-ssh-sign.yml](../../playbooks/openbao-ssh-sign.yml); их
соединение и есть вход, который выполняется руками по одному разу на хост.

Сам ключ лежит в OpenBao по пути `infra/ssh_ca` и читается на контроллере:
ноды до OpenBao не достают, его API живёт в docker-сети панели, а не в меше.
Передают его ноде двое —
[playbooks/provision-node.yml](../../playbooks/provision-node.yml) при сборке,
чтобы нода была полноценным членом флота с самого начала, и
[playbooks/ssh-ca-trust.yml](../../playbooks/ssh-ca-trust.yml) для той, что уже
существует.

## Отказ от паролей

Третья необязательная задача роли, выключенная, пока
`ssh_hardening_disable_password_auth` не поднят. Пишет
`/etc/ssh/sshd_config.d/30-ansible-auth.conf` — три директивы и больше ничего.

`KbdInteractiveAuthentication no` рядом с `PasswordAuthentication no` не
избыточен. С одним только вторым PAM продолжает принимать пароль через
keyboard-interactive, и хост числится усиленным, оставаясь ровно настолько же
доступным, насколько был. Обе строки, всегда.

`PermitRootLogin` по умолчанию `prohibit-password`, а не `no`. Root остаётся
достижим **по ключу** — админским ключом провайдера, аварийным входом, который
не зависит ни от OpenBao, ни от NetBird, ни от этой роли. Закрывать и эту дверь
— отдельное решение, и принимать его надо, понимая, что единственным путём
назад останется консоль хостера.

**Это единственная настройка здесь, после которой до хоста может не добраться
никто**, поэтому она выключена по умолчанию и выкатывается по одной ноде. Её
охраняют две проверки, и они разного рода:

- Пользователю автоматизации проверка не нужна. Роль в момент записи файла уже
  выполняется по SSH с ключом — это и есть доказательство, что ключевой вход на
  этом хосте работает.
- Root'у нужна. Роль читает `/root/.ssh/authorized_keys` и отказывается ставить
  `prohibit-password`, если файла нет или он пуст: на таком хосте пароль и есть
  единственный вход для root, и выключить его значило бы убрать аварийный
  выход, а не усилить защиту.

Значение `yes` или `no` нужно закавычить — YAML читает их как булевы, и роль
проверяет это до того, как что-либо записать.

`sshd -T` печатает не всегда то, что написано в файле. OpenSSH держит
`PermitRootLogin` таблицей, где несколько имён означают одно значение, и
выводит первое подходящее имя; в версиях OpenSSH из Debian 12 и 13 в этой
таблице `without-password` стоит раньше `prohibit-password`, поэтому наш конфиг
читается обратно старым написанием. В апстриме их с тех пор поменяли местами —
именно поэтому `vars/main.yml` сопоставляет настройке **список** допустимых
написаний, а не одну строку.

Потом читается `sshd -T`, как и для CA. Здесь это важнее: drop-in, который sshd
не включил, оставляет хост принимающим пароли, тогда как всё остальное говорит
обратное. Отсутствующий CA всего лишь не добавляет способ входа; здесь не
убирается существующий — а это отказ, выглядящий как успех.

Применяют двое.
[playbooks/provision-node.yml](../../playbooks/provision-node.yml) поднимает
флаг внутри плея базовой системы, поэтому нода запирается по мере сборки — там
это безопасно, потому что плей уже подключён ключом автоматизации, а
предшествующий ему bootstrap дошёл до root тоже по ключу.
[playbooks/ssh-lockdown.yml](../../playbooks/ssh-lockdown.yml) — для уже
существующих нод, по одной. Перезагрузка конфига не рвёт соединение, в котором идёт прогон,
поэтому открой к хосту новую сессию, прежде чем идти дальше.

## Собственный сертификат хоста

Четвёртая необязательная задача и вторая сторона того же CA. `TrustedUserCAKeys`
позволяет ноде поверить пользователю; `HostCertificate` позволяет пользователю
поверить ноде.

Выключена, пока роли не дали токен OpenBao и хотя бы один домен. Нода до OpenBao
не достаёт, поэтому запрос на подпись делегируется контроллеру — сама нода лишь
читает свой публичный хостовой ключ и получает сертификат обратно.

**Подключаться надо по имени, иначе смысла нет.** OpenBao сверяет хостовые
принципалы с `allowed_domains` и больше ни с чем, так что сертификат не может
покрыть голый адрес. Нода, к которой пришли по IP, проверяется по-старому, что
бы она ни предъявила.

Клиенту нужна одна строка в `known_hosts`, и пока её нет, для него ничего не
меняется:

```
@cert-authority *.mesh.example,*.public.example ssh-rsa AAAA…  # ключ из infra/ssh_ca
```

### Когда переподписывает

Два условия, и второе легко упустить:

- осталось меньше `ssh_hardening_host_cert_renew_days` дней, либо
- в сертификате нет принципала, который хост должен заявлять.

После переезда флота на другой домен сертификат продолжает работать — он
подписан и не просрочен, — но называет имя, которое никто больше не набирает.
Проверка по сроку этого не заметит никогда.

**Лишний** принципал сознательно не трогается. При переезде старое имя должно
работать, пока все клиенты не переведены, и переподписать его прочь — ровно то,
что сломало бы этот период.

Остаток срока измеряется **на ноде**, её же `ssh-keygen` и её же часами. Разбор
метки времени на контроллере сравнивал бы одно местное время с другим, а флот
в одном часовом поясе не живёт — ошибка, которая всплыла бы через месяцы
сертификатом, переподписанным рано или не переподписанным вовсе.

### Продление не по расписанию

Сертификат обновляется, когда выполняется роль, а роль выполняется, когда её
попросят. Девяносто дней выбраны, чтобы этот разрыв был переживаем, а не чтобы
он был правильным. Лечится периодическим шаблоном, которого пока нет.

## Переменные

| Переменная | По умолчанию | Описание |
|------------|--------------|----------|
| `ssh_hardening_mesh_port` | `automation_ssh_port` (2200) | Дополнительный порт sshd для автоматизации через меш; общий с ролью ufw через group_vars/all |
| `ssh_hardening_public_port` | `22` | Канонический публичный порт sshd в drop-in'е; переопределить на хостах, сознательно ушедших с 22 |
| `ssh_hardening_ca_public_key` | `""` | Публичный ключ CA флота (`infra/ssh_ca` в OpenBao). Пусто — учётные данные sshd не меняются; значение ставит доверие к сертификатам рядом с `authorized_keys` |
| `ssh_hardening_ca_path` | `/etc/ssh/trusted-user-ca.pub` | Куда этот ключ пишется. Публичен по построению, читаем всеми |
| `ssh_hardening_disable_password_auth` | `false` | Убрать вход по паролю и парольный root. По умолчанию выключено — единственная настройка здесь, способная запереть всех снаружи |
| `ssh_hardening_permit_root_login` | `prohibit-password` | Что позволено root после отказа от паролей. `no` закрывает и ключевой путь, и требует осознанной замены |
| `ssh_hardening_openbao_token` | `""` | Токен для подписи хостового ключа. Пусто — личность хоста не трогается |
| `ssh_hardening_host_domains` | `[]` | Домены, которые заявляет хост; на каждый принципал `<inventory_hostname>.<домен>` |
| `ssh_hardening_host_cert_renew_days` | `30` | Переподписать, когда осталось меньше стольких дней |
| `ssh_hardening_host_cert_path` | `/etc/ssh/ssh_host_ed25519_key-cert.pub` | Куда пишется сертификат |

## Зависимости

Нет. В паре с ролью `ufw` (`ufw_mesh_tcp`) порт остаётся mesh-only.

## Пример

```yaml
- hosts: fleet
  become: true
  roles:
    - ssh_hardening
```

## Поддерживаемые ОС

Debian 12/13, Ubuntu 24.04.
