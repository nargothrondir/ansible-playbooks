# Роль: dns

[🇬🇧 English](README.md) · 🇷🇺 Русский

## Описание

Шифрованный DNS для **собственных** запросов хоста — apt, ACME, панель,
mesh-имена. Настраивает `systemd-resolved` на DNS-over-TLS к выбранным
апстримам и убирает серверы, назначенные интерфейсом, которые иначе их
перекрывают.

DNS клиентов VPN роль **не трогает**: их трафик резолвит сам xray по DoH, и
этот путь до системного резолвера не доходит.

### Роль ставит резолвер, потому что конвейер этого не делал

На Debian 12+ `systemd-resolved` — **отдельный пакет**, в минимальной установке
его нет. На всех собранных руками нодах он появился вручную. На ноде,
собранной целиком конвейером, резолвера не оказалось вовсе — и NetBird, не
найдя его, забрал `/etc/resolv.conf` себе обычным файлом и стал пересылать
запросы туда, что было прописано в образе провайдера, **открытым текстом**:

```
un  systemd-resolved  <none>          ← пакет не установлен
:53 → только netbird
/etc/resolv.conf (обычный файл):  nameserver 100.64.0.0
```

То есть нода, переустановленная через конвейер, **молча** теряет шифрование
DNS — не ломается, просто перестаёт его иметь. Поэтому роль ставит пакет,
передаёт `resolv.conf` стабу и перезапускает NetBird, чтобы тот
перерегистрировал mesh-домен в новом резолвере вместо владения файлом. На
хосте, где всё это уже есть, каждый шаг — no-op.

Порядок не случаен: апстримы настраиваются **до** того, как resolved станет
авторитетным, иначе в промежутке между двумя шагами сломается любой запрос.

Заменяемый `resolv.conf` сначала копируется в
`/etc/resolv.conf.before-dns-role`. Если передача владения пойдёт не так,
восстановление этого файла и перезапуск NetBird возвращают резолв.

### Половина, которую легко упустить

`systemd-resolved` резолвит по **областям**, и собственные серверы интерфейса
выигрывают у глобальных. Образы провайдеров прописывают `dns-nameservers` в
конфигурации интерфейса; `ifupdown` передаёт их в `resolvectl` (в Debian 13
`/sbin/resolvconf` — символическая ссылка на него), интерфейс получает свои
резолверы, и все запросы уходят туда.

Глобальная конфигурация после этого не применяется ни к чему — при том что
`resolvectl status` её показывает и выглядит всё правильно. Спрашивать надо сам
линк:

```bash
resolvectl dns ens3
# Link 2 (ens3): 203.0.113.53 198.51.100.53   ← свои серверы, и они выигрывают
```

По `resolvectl query` это читать **нельзя**. Его пометка `-- link: ens3`
называет интерфейс, через который достижим *возвращённый адрес*, а не область,
которая ответила: линк вообще без DNS-серверов и без DNS-области всё равно
проставляет своё имя в каждом ответе. Это заблуждение стоило здесь целого
вечера, и отчёт самой роли его повторял.

Поэтому роль делает две вещи, и вторая — то, что делает первую настоящей:
пишет drop-in и снимает серверы с линка.

### DoT, а не DoH

`systemd-resolved` умеет DNS-over-TLS и **не умеет** DNS-over-HTTPS. Это два
транспорта для одной задачи, а не два уровня защиты — включить оба значит
добавить путь отказа, не добавив приватности.

- **DoT** — порт 853. Опознаётся как DNS с первого пакета и блокируется одной
  строкой фильтра, зато поддержан здесь изначально, без лишнего процесса.
- **DoH** — порт 443, заблокировать сложно, не сломав веб; ценой становится
  постоянно работающий демон, который уносит DNS с собой, когда падает.

По умолчанию DoT; DoH — только там, где 853 реально режут. Это решение по
конкретному хосту, а не стандарт для всего флота.

### Какие резолверы и почему эти

Два независимых оператора как основные, у каждого оба anycast-адреса и обе
версии протокола; Google — только запасной. `systemd-resolved` перебирает
список по порядку и остаётся на том, кто ответил, так что это порядок
предпочтения, а не пул.

**Cloudflare первым** по задержке — самая широкая anycast-сеть, а каждый
здешний запрос лежит на критическом пути apt, ACME и связи с панелью.
**Quad9 вторым** ради независимости: другой оператор, швейцарский фонд,
валидирует DNSSEC. **Google последним**, потому что самый доступный резолвер в
интернете — правильный запасной вариант и неправильный основной.

Записи IPv6 здесь не для красоты. Ноды двухстековые, и список только из IPv4
превращает сбой IPv4, который нода пережила бы, в полный отказ DNS.

Альтернативы для хоста, где основные режут — Mullvad, dns0.eu, AdGuard —
перечислены в `defaults/main.yml`. Задавай `dns_servers` в `host_vars` этого
хоста, а не меняй умолчание для всего флота. И учти: **фильтрующий** резолвер
отвечает NXDOMAIN на то, что блокирует, а ноде нужно резолвить реестры,
зеркала и endpoint'ы ACME, а не мнения о них.

### Роль заменяет список резолверов, а не дополняет его

На хосте, где резолвер настраивали руками, в `/etc/systemd/resolved.conf` уже
лежат `DNS=` и `FallbackDNS=`. Приоритет у drop-in'а выше, но настройки-**списки**
в systemd не заменяются, а накапливаются по файлам — а главный файл читается
первым, поэтому его серверы оказываются в начале списка, там, где их
предпочитают. Drop-in выглядел бы главным, пока отвечали бы старые серверы.

Измерено на лабораторной ноде, потому что руководство не описывает ни
накопления, ни лечения:

```
главный файл:  DNS=203.0.113.53
drop-in:       DNS=<шесть серверов>
результат:     DNS Servers: 203.0.113.53 <шесть серверов>   ← старый первым
```

Поэтому шаблон сбрасывает каждый список пустым присваиванием перед тем, как его
задать. С отдельной строкой `DNS=` впереди тот же тест даёт только серверы из
drop-in'а. Главный файл роль по-прежнему не трогает.

## Переменные

| Переменная | По умолчанию | Описание |
|------------|--------------|----------|
| `dns_servers` | Cloudflare, Quad9 (с именами) | Апстримы по приоритету. Суффикс `#hostname` позволяет проверить сертификат по имени. |
| `dns_fallback_servers` | `8.8.8.8#dns.google` | Только когда недоступны все серверы выше. |
| `dns_over_tls` | `true` | Строгий DoT — без тихого отката в открытый текст. |
| `dns_dnssec` | `true` | Строгая валидация. `allow-downgrade` — предпочесть доступность подлинности. |
| `dns_search_domain` | `~.` | Делает апстримы авторитетными для доменов, которые не забрала другая область. |
| `dns_manage_resolv_conf` | `true` | Ставить резолвер и направлять `/etc/resolv.conf` на его стаб, перезапуская NetBird для перерегистрации. |
| `dns_stub_resolv_conf` | `/run/systemd/resolve/stub-resolv.conf` | Куда указывает этот симлинк. |
| `dns_allow_running_containers` | `false` | Выполняться, даже если контейнеры подняты. До перезапуска у них остаётся старый резолвер — см. ниже. |
| `dns_strip_interface_nameservers` | `true` | Убрать `dns-nameservers` из файла интерфейсов и очистить DNS линка. |
| `dns_interfaces_file` | `/etc/network/interfaces` | Где эти строки лежат. |
| `dns_verify_name` | `deb.debian.org` | Имя, резолвящееся после применения, чтобы доказать работоспособность. |

## Что проверяется до отчёта об успехе

Записанная конфигурация — не то же самое, что действующая, поэтому роль
проверяет поведение:

- `resolvectl` сообщает `+DNSOverTLS`;
- `dns_verify_name` резолвится;
- собственное `<имя>.<netbird_dns_domain>` этого хоста по-прежнему резолвится,
  если переменная задана **и NetBird установлен** — mesh это путь, которым
  панель достаёт ноду, и глобальная область, проглотившая mesh-домен, оставит
  ноду обслуживающей трафик, но неуправляемой. Вторая половина условия важна:
  `netbird_dns_domain` приходит из `group_vars`, то есть задана и на ноде,
  которая в mesh никогда не входила, — включая ноду в процессе провижена, где
  роль отрабатывает до роли `netbird`.

Последняя debug-строка называет апстрим, на котором остановилась глобальная
область, и сообщает, сохранил ли основной линк собственные серверы, — так что
выигравший линк виден, а не выводится догадкой.

## Три способа получить проблему

**У запущенных контейнеров остаётся старый резолвер.** Docker копирует
`/etc/resolv.conf` в контейнер в момент его **создания** и больше к файлу не
возвращается. Подмена хостового файла оставляет каждый работающий контейнер с
адресом резолвера, который был раньше, — а он перестаёт отвечать, как только
NetBird перерегистрируется в `systemd-resolved`. Во время плея не падает ничего:
роль проверяет хост, и хост в порядке. Просто контейнеры перестают резолвить, и
на ноде Remnawave первое, чему понадобится DNS, — продление сертификата, через
два месяца.

Измерено на лабораторной ноде, один и тот же ACME-хук по обе стороны от роли:

```
02:29:00  added TXT _acme-challenge...                     ← до
04:40:43  ERROR ... Temporary failure in name resolution   ← после
```

Поэтому роль **останавливается**, обнаружив запущенные контейнеры. Лечится это
их перезапуском, и только им; задай `dns_allow_running_containers=true`, когда
перезапуск запланирован.

Останавливается только тогда, когда передача владения действительно предстоит.
Вопрос не «есть ли контейнеры», а «собирается ли роль забрать у них резолвер»:
если `/etc/resolv.conf` уже указывает на стаб, ничего из того, на что они
опираются, не меняется, и проверка пропускается. Без этого различия guard
обрывал любой повторный запуск `provision-node.yml` на ноде, которую конвейер
уже собрал.

Перезапуска достаточно для обоих типов сети — сказать это стоит, потому что
документация наводит на обратное. Контейнер в **host-сети** получает копию
хостового файла как есть и достаёт `127.0.0.53` через общее сетевое
пространство. Контейнер в **пользовательской bridge-сети** хостовых серверов не
видит вовсе: ему достаётся встроенный резолвер Docker на `127.0.0.11`, который
пересылает внешние запросы из сетевого пространства хоста, так что стаб работает
и там. Откат Docker на открытый `8.8.8.8` касается только **дефолтной** сети
`bridge`, а её здесь не использует никто. Измерено на обоих; цифры в issue #153,
который теперь отслеживает лишь то, должна ли роль перезапускать контейнеры
сама.

**У строгого DoT нет запасного плана.** Если выбранные апстримы недоступны,
резолв не деградирует в открытый текст, а перестаёт работать — ни apt, ни ACME,
ни обращение к панели по имени. Опечатка в `dns_servers` снимает ноду с сети по
именам.

**В файле интерфейсов лежит статический адрес.** Роль удаляет только строки с
`dns-nameservers` и делает резервную копию; файл целиком она не переписывает.
Небрежная правка там оставит хост недоступным после перезагрузки, и лечиться
это будет только через консоль провайдера.

Серверы линка снимаются через `resolvectl revert` — он трогает резолвер, а не
интерфейс: перезапуск интерфейса оборвал бы SSH-сессию, в которой идёт плей.

## Зависимости

Нет. Требуется, чтобы активным резолвером был `systemd-resolved`; роль это
проверяет, а не предполагает.

## Пример

```yaml
- hosts: fleet
  become: true
  roles:
    - role: dns
      vars:
        dns_servers:
          - "9.9.9.9#dns.quad9.net"
```

## Supported OS

Debian 12/13, Ubuntu 22.04/24.04 (`os_family == 'Debian'`).
